= Plan: replace API tokens with the `gh` and `glab` CLIs
:toc: macro

Base branch: `claude/zealous-johnson-rfqa12` (commit `6c2e7a1`).
Status: proposal. No code is changed on this branch yet.

toc::[]

== Summary

repo-stats can stop handling tokens completely.
It can call `gh api` and `glab api` as subprocesses and never read, hold, send or print a credential.
The tokens still exist, but `gh` and `glab` own them, in the OS keychain locally and in the CI runner's environment in CI.

This removes a whole class of bugs from the tool, and it is a real improvement for local use.
In CI the improvement is smaller, because the token still sits in an environment variable there.
One caveat matters for the design: neither CLI is safe if you point it at an arbitrary host (see <<verified>>).
So repo-stats must keep its host allowlist and must always pass `--hostname` itself.

== Goals

* repo-stats never reads, stores, sends, logs or names the value of a credential.
* Locally, a user who has run `gh auth login` or `glab auth login` once runs the tool with no extra setup.
* Git-only mode still needs nothing but Python and git.
* CI needs one documented environment line or one login step, and nothing more.
* No credential can reach a host the user did not choose, whatever the repository's remote says.

[[verified]]
== Verified CLI behaviour

These results come from gh 2.103.2 and glab 1.124.0, tested against a local listener that logs request headers.
The plan depends on them.

[cols="1,3"]
|===
| Behaviour | Consequence for repo-stats

| `gh` sends `GH_TOKEN` and `GITHUB_TOKEN` only to `github.com` and `*.ghe.com`.
| A crafted remote cannot leak a github.com token.

| `gh` sends `GH_ENTERPRISE_TOKEN` to *any* host passed with `--hostname`.
| repo-stats must not take the hostname from an untrusted remote.

| `glab` sends `GITLAB_TOKEN` to *any* host passed with `--hostname`, including a host it never logged in to.
| Same rule: the hostname must come from the allowlist or from an explicit flag.

| Without `--hostname`, `glab api` uses the host of the git repository in its *working directory*. With a crafted remote it sent `GITLAB_TOKEN` there, and also sent a telemetry call (`usage_data/track_event`) to that host with the token attached.
| Always pass `--hostname`. Run the CLI from a neutral directory, never from the analysed repo. Set `GLAB_SEND_TELEMETRY=false`.

| An explicit `--hostname gitlab.com` was respected, even with the crafted repo as the working directory.
| The fix above is enough.

| `-F key=@path` (both CLIs) reads a local file and sends its contents. `-F` also expands `{owner}`/`:fullpath` placeholders from the current repository.
| Pass every value with `-f` (raw string), never `-F`.

| `gh` exits 4 when not authenticated and prints `gh auth login` advice. API errors exit 1, print `gh: <message> (HTTP <code>)` to stderr, and print the JSON body to stdout. `glab` does the same with exit 1.
| Exit codes and stderr are enough to map errors to clear messages.

| `glab` with `GLAB_ENABLE_CI_AUTOLOGIN=true` in GitLab CI authenticates every command, `glab api` included, with `CI_JOB_TOKEN` (checked in glab's source, `internal/config/config_mapping.go`).
| GitLab CI can run on the short-lived job token instead of a long-lived PAT. The current code cannot do this, because it sends `PRIVATE-TOKEN` and the job token needs `JOB-TOKEN`.

| The GitLab job token can call `GET /projects/:id/merge_requests` and `GET .../merge_requests/:iid/notes`, but *not* `.../merge_requests/:iid/commits`, and it cannot call GraphQL.
| Keep GitLab on REST. Degrade gracefully when the commits endpoint is refused.
|===

== Is it more secure?

=== What gets better

* *No credential code in repo-stats.*
  `resolve_token`, `http_json`, the redirect guard, the proxy bypass, the insecure-URL check and the token error messages all go, about 150 lines.
  Each of these existed only to stop the tool leaking a token, and each was a place a bug could hide.
  The tests for them (`B3_Tokens`, the loopback-proxy tests) were needed for the same reason.
* *No token in the shell.*
  The README now suggests `GITLAB_TOKEN=glpat-... python3 ...`, which writes the token into shell history.
  It also suggests `GITHUB_TOKEN=$(gh auth token) ...`, which puts it in the environment of every process the tool starts, every `git` call included.
  With `gh auth login` or `glab auth login`, the token stays in the OS keychain and is read only by the CLI, only for the request.
* *No pasted PATs.*
  Both CLIs support browser and device-code OAuth, so users never copy a token at all.
  `gh` can also use expiring, auto-refreshed tokens (`--expiring`).
* *GitLab CI can use the job token.*
  It is valid only while the job runs and is masked in logs, so a long-lived token in a CI variable becomes optional.
* *TLS, proxies, redirects and enterprise CAs are handled by the vendors' maintained HTTP stacks.*
  repo-stats no longer handles them itself.

=== What does not get better, or gets worse

* *The token still exists.*
  Any process running as the same user can run `gh auth token`.
  A malicious or compromised copy of repo-stats could do this, so the change protects against accidental leaks, not against a hostile tool.
  The same was true before.
* *Broader default scopes.*
  `gh auth login` asks for at least `repo`, `read:org` and `gist`, and `repo` gives write access to every private repository.
  `glab`'s OAuth login asks for `api` and `write_repository`.
  A user who carefully made a read-only, fine-grained token loses least privilege by switching to the default login.
  See <<least-privilege>> for how to keep it.
* *CI is mostly unchanged.*
  The CLI still reads the token from an environment variable, and that variable is still visible to every process in the step that sets it.
  The gain in CI is less credential code, plus the GitLab job token.
* *New dependency.*
  API mode now trusts the `gh` or `glab` binary and its update channel, a larger supply chain than the Python standard library.
  Git-only mode is unaffected.
* *Unsafe CLI defaults (see <<verified>>).*
  These are why the host allowlist cannot be removed.

Verdict: the change is worth making.
It removes every token from repo-stats and from users' shell habits, and enables job-token auth in GitLab CI.
The remaining risks are explained in <<gaps>>.

== Design

=== User-facing changes

[cols="1,3"]
|===
| Removed | `--token-env`, `--api-url`, and reading `GITHUB_TOKEN`, `GH_TOKEN`, `GITLAB_TOKEN` and `GITLAB_PRIVATE_TOKEN`.
| Added | `--hostname HOST`: the GitHub Enterprise or self-managed GitLab host. It is passed to the CLI as `--hostname`.
| Unchanged | `--provider`, `--source auto/git/api`, and every other flag.
|===

Behaviour of `--source auto` (the default):

. Find the provider and host (next section). If neither is found, use git mode and show a warning.
. If the CLI is not on `PATH`, use git mode and warn: "Install gh (https://cli.github.com) for exact PR data."
. Call the API. If the CLI says it is not authenticated (gh exit 4, or HTTP 401), use git mode and warn: "Run `gh auth login`" (or the glab equivalent, or set the CI variable).

With `--source api`, each of these is an error instead of a fallback.

There is no "is the user logged in?" pre-check.
`gh auth status` makes its own network call and is not needed, because the first real request answers the same question.

=== Host selection (keeps the current trust model)

* The remote host is `github.com` or `gitlab.com`: use it, and pass `--hostname github.com` or `--hostname gitlab.com`.
* Any other remote host: API mode needs `--provider` plus `--hostname`, given by the user.
  Never derive the host from the remote, because `GH_ENTERPRISE_TOKEN`, `GITLAB_TOKEN` and `CI_JOB_TOKEN` would go to it.
* Optional convenience for self-managed CI: trust the remote host when it equals `CI_SERVER_FQDN` (with `GITLAB_CI=true`), or the host of `GITHUB_SERVER_URL` (with `GITHUB_ACTIONS=true`).
  The runner sets these variables, and anyone who can change them already controls the job.

=== One subprocess helper

The new `run_cli(tool, host, args)` replaces `http_json`. It:

* resolves the binary once with `shutil.which` and runs it from its absolute path, with `shell=False` and an argv list.
* sets `cwd` to a fresh temporary directory, so neither CLI can read the analysed repository's remotes or placeholders.
* always puts `--hostname <host>` in argv.
* passes only `-f key=value` (raw strings), never `-F`, `--input`, `--form` or placeholders.
  The GraphQL query is a constant, and REST paths are built from `urllib.parse.quote(..., safe="")` components.
* copies `os.environ` and adds `GH_PROMPT_DISABLED=1`, `GH_NO_UPDATE_NOTIFIER=1`, `GLAB_SEND_TELEMETRY=false`, `GLAB_CHECK_UPDATE=false` and `NO_COLOR=1`.
  It removes `GH_DEBUG`, `DEBUG`, `GLAB_DEBUG` and `GLAB_DEBUG_HTTP`, so stderr (which the tool may quote in errors) cannot contain request dumps.
  It never reads or sets a token variable.
* uses a timeout per call. It retries with backoff when stderr ends in `(HTTP 429)` or `(HTTP 5xx)`, keeping today's backoff policy.
* maps errors to messages: exit 4 or HTTP 401 → "not logged in; run `gh auth login` / `glab auth login`, or set `GH_TOKEN` / use `GLAB_ENABLE_CI_AUTOLOGIN` in CI"; 403 → no access or rate limit; 404 → not found or no access.
  It quotes at most the CLI's one-line stderr summary, never stdout.
* parses stdout as JSON. A GraphQL `errors` array is reported as today.

=== GitHub

The query is the existing `GITHUB_QUERY`, unchanged.
The tool keeps its own pagination loop, so it can still stop early on `--since` and `--max-prs`.

[source]
----
gh api graphql --hostname github.com -f query=<GITHUB_QUERY> -f owner=<owner> -f name=<name> [-f cursor=<endCursor>]
----

`gh` sends GraphQL to `/api/graphql` on Enterprise hosts by itself, so `--api-url` has no equivalent.

=== GitLab

The tool stays on REST, because the job token cannot call GraphQL.
Each call passes `--method GET`, so `-f` fields become query parameters and nothing goes into the URL by hand.

[source]
----
glab api --hostname gitlab.com --method GET projects/<quoted path>/merge_requests -f state=all -f scope=all -f order_by=updated_at -f sort=desc -f per_page=100 -f page=<n> [-f updated_after=...] [-f target_branch=...]
glab api --hostname gitlab.com --method GET projects/<quoted path>/merge_requests/<iid>/commits -f per_page=100
glab api --hostname gitlab.com --method GET projects/<quoted path>/merge_requests/<iid>/notes -f sort=asc -f order_by=created_at -f per_page=100
----

* Pagination: stop when a page has fewer than `per_page` items, instead of reading `X-Next-Page`. This avoids parsing headers out of `--include` output.
* The per-MR detail calls keep the existing 8-worker thread pool, now spawning one process per call.
* If `.../commits` returns 403 or 404 (the job-token case), stop calling it.
  Take `first_commit` and `commits` from the local merge-commit graph where one exists (`claims`), add `"first_commit"` to `inferred`, and add one dashboard warning.
  Squash-merged MRs then have no coding time, and the warning says so.

=== Git subprocesses

`git_cmd` and `stream_git` pass an environment with credential variables removed: `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `GITLAB_TOKEN`, `GITLAB_ACCESS_TOKEN`, `GITLAB_PRIVATE_TOKEN`, `OAUTH_TOKEN` and `CI_JOB_TOKEN`.
The tool removes them by name and never reads their values.
Git needs none of them, so a malicious hook, filter or `textconv` driver in an untrusted repository cannot read them through git.

=== Code removed from `repo_stats.py`

`_SameHostRedirect`, `_OPENER`, `_DIRECT_OPENER`, `_is_loopback`, `http_json`, `resolve_token`, `--token-env`, `--api-url`, the token-name log line, and the `urllib.request`, `urllib.error`, `http.client`, `email.utils` and `socket` imports where nothing else uses them.
`_retry_after` goes too, because the CLIs do not expose `Retry-After` without `--include`.
A fixed backoff replaces it.

== Implementation steps

. Add `run_cli` and the error mapping, with unit tests that use fake CLIs (next step).
. Add fake `gh` and `glab` executables to the tests.
  These are small Python scripts placed first on `PATH`.
  Each one records its argv, cwd and environment to a JSON log, then answers by calling the existing `mock_servers.github_handler` and `gitlab_handler` functions with a request dict built from argv.
  The fixtures stay as they are, and the tests stay stdlib-only and offline.
  A Windows variant of the scripts is not needed for CI on Linux and macOS.
. Port `fetch_github` to `run_cli`. Port the `B1_GitHub` tests.
. Port `fetch_gitlab` to `run_cli`, including the job-token fallback for commits. Port the `B2_GitLab` tests.
. Replace the host and token logic in `collect()` with the host-selection rules above, and add `--hostname`.
  Remove `--token-env` and `--api-url`.
  Since the tool is at 0.1.0, make them hard errors that explain the new flag rather than keeping aliases.
. Strip credential variables from git subprocess environments.
. Replace `B3_Tokens` with tests that assert:
** every CLI call has `--hostname`, uses no `-F`, `--input`, `--form` or placeholder syntax, and runs from a cwd outside the repository.
** a remote such as `github.evil.example` or `gitlab.evil.example` with no `--hostname` never starts a CLI.
** `GLAB_SEND_TELEMETRY=false` is set, and the debug variables are removed.
** git child processes see none of the credential variables (a fake `git` wrapper on `PATH` can record the environment).
** a missing CLI, gh exit 4, and HTTP 401/403/404 each give the right fallback (auto) or error (api).
** a refused `.../commits` call in GitLab degrades with one warning.
. Delete the loopback-proxy and redirect tests, which covered code that no longer exists.
. Add an opt-in live smoke test, skipped unless `REPO_STATS_LIVE=1`, that runs real `gh` against a small public repository.
. Update the README (Quick start, "Where the data comes from", Security), the `--help` epilog, and the template's "Run with an API token" hint, which becomes "Install and log in to gh or glab".

[[usage]]
== How users will run it

=== Locally

[source,sh]
----
# one-time, if not already done
gh auth login                       # or: glab auth login
# every run, with no tokens and no env vars
python3 repo-stats/repo_stats.py /path/to/repo --serve

# GitHub Enterprise / self-managed GitLab
gh auth login --hostname ghe.example.com
python3 repo-stats/repo_stats.py /path/to/repo --provider github --hostname ghe.example.com
----

If neither CLI is installed, the tool still works in git-only mode and says so on the dashboard.

=== GitHub Actions

`gh` is preinstalled on GitHub-hosted runners. It needs the workflow token passed in explicitly.

[source,yaml]
----
permissions:
  contents: read
  pull-requests: read
jobs:
  stats:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0            # full history and tags
      - uses: actions/checkout@v4
        with:
          repository: husam-e/scripts
          path: tools
      - run: python3 tools/repo-stats/repo_stats.py . -o repo-stats.html
        env:
          GH_TOKEN: ${{ github.token }}   # read by gh only, never by repo-stats
      - uses: actions/upload-artifact@v4
        with:
          name: repo-stats
          path: repo-stats.html
----

`github.token` is created for the job and expires when it ends.
`permissions:` limits it to read access.
Set `GH_TOKEN` on this step only, not at job level, so other steps never see it.
To analyse a different private repository, use a GitHub App installation token (for example from `actions/create-github-app-token`), not a PAT.

=== GitLab CI

[source,yaml]
----
repo-stats:
  image: registry.gitlab.com/gitlab-org/cli:v1.124.0   # Alpine with glab and git; pin a version
  variables:
    GIT_DEPTH: 0                     # full history
    GLAB_ENABLE_CI_AUTOLOGIN: "true" # glab authenticates with CI_JOB_TOKEN
  script:
    - apk add --no-cache python3
    - git clone --depth 1 https://github.com/husam-e/scripts.git /tmp/tools
    - python3 /tmp/tools/repo-stats/repo_stats.py . -o repo-stats.html
  artifacts:
    paths: [repo-stats.html]
----

The job token can list MRs and read their notes, but not their commits, so squash-merged MRs have no coding time.
For full data, store a project access token with only the `read_api` scope and a short expiry as a masked, protected CI/CD variable.
Name it `GITLAB_TOKEN`, and glab will prefer it over the job token.
On self-managed GitLab, add `--provider gitlab --hostname $CI_SERVER_FQDN` (or rely on the optional `CI_SERVER_FQDN` rule above).

=== A remote job (cron VM, Kubernetes CronJob, Jenkins, and so on)

Provide the token to the CLI's process only, from your secret store, for the duration of the run:

[source,sh]
----
# Kubernetes: mount the secret as an env var on the container
# Jenkins:   withCredentials([string(credentialsId: 'gh-read', variable: 'GH_TOKEN')]) { sh '...' }
# systemd:   LoadCredential=gh-token:/etc/creds/gh-token, then in the unit's script:
GH_TOKEN="$(cat "$CREDENTIALS_DIRECTORY/gh-token")" python3 repo_stats.py /srv/repo -o /srv/out/stats.html
----

Use one of these, from best to worst:

. A *GitHub App* installation token, minted for each run (it expires within an hour), with read-only Pull requests and Contents permissions on only the repositories it needs.
  For GitLab, use a project or group access token with `read_api`, a short expiry and rotation.
. A *fine-grained* PAT with read-only Pull requests and Contents on only the target repositories, with an expiry.
. Avoid `gh auth login` and `glab auth login` on headless servers.
  With no OS keyring, both CLIs fall back to writing the token in plain text (`~/.config/gh/hosts.yml`, `~/.config/glab-cli/config.yml`).
  If you must use them, run the job as a dedicated user and check that the file has mode 600.

The repository clone needs only read access to git.
Use a deploy key or the same short-lived token through a credential helper, not a token embedded in the remote URL.

[[least-privilege]]
== Keeping least privilege on a laptop

`gh auth login` cannot request fewer scopes than `repo`, `read:org` and `gist`.
To use a read-only token without putting it in your shell:

* GitHub: create a fine-grained, read-only PAT, then run `gh auth login --with-token < file` and delete the file.
  `gh` stores the token in the keychain.
  The gh help warns that fine-grained tokens can confuse some *other* gh commands, so a separate gh account or config dir (`GH_CONFIG_DIR`) keeps your main login untouched.
* GitLab: create a PAT with only the `read_api` scope, then run `glab auth login --stdin < file`. glab stores it in the keyring when one is available.

[[gaps]]
== Remaining security gaps

. *Same-user access.* Anything running as you can ask `gh` or `glab` for the token. Moving to the CLIs does not change this.
. *Scope.* Default CLI logins are read-write across all of your repositories. Mitigate as in <<least-privilege>>.
. *Host trust depends on repo-stats.* Both CLIs send environment tokens to whatever host they are given, and glab follows the working directory's remote. The allowlist, the explicit `--hostname` and the neutral `cwd` are what prevent leaks, and the tests must pin all three.
. *A wrong but explicit `--hostname` is trusted.* A user who passes `--hostname evil.example` with `GH_ENTERPRISE_TOKEN` or `GITLAB_TOKEN` set will send it there. This is the same as `--api-url` today. Documentation is the only defence.
. *CI environment exposure.* In CI the token is an environment variable, readable by every process in that step. Scope it to the one step, use the job's own short-lived token, and do not run untrusted code in the same step.
. *Plain-text fallback.* On headless machines with no keyring, `gh` and `glab` write tokens to plain-text config files. In GitLab CI, glab always stores to the config file, not the keyring.
. *Supply chain.* API mode trusts the `gh` or `glab` binary on `PATH`. On Windows, Python can find an executable in the current directory before `PATH`. Running from a neutral `cwd` with an absolute path from `shutil.which` reduces this, but whether `which` itself checks the current directory depends on the Python version and the `NoDefaultCurrentDirectoryInExePath` setting, so it does not remove the risk.
. *Untrusted repositories.* `git` itself can run commands configured in a repository's `.git/config` (for example a `textconv` driver). Removing credential variables from git's environment limits the damage, but analysing a repository you do not trust is still risky. This is unchanged, and unrelated to tokens.
. *Output data.* The HTML, JSON and CSV contain PR titles, branch names and timings, but no credentials. `--no-titles` remains the tool for sharing.
